RateApp

招待制の建物レビュー API

招待コードで登録し、建物を登録・検索する。登録された建物にレビューを投稿し、ほかの利用者のレビューに「いいね」を付けられます。

主な API
ログイン
POST /api/auth/login
建物一覧
GET /api/buildings/getall
レビュー投稿
POST /api/reviews/add
いいねの切り替え
POST /api/likes/toggle

利用の流れと API の構成

未使用の招待コードでアカウントを作成し、登録済みの端末シリアル番号でログインします。取得した JWT を Bearer トークンとして送信すると、認証が必要な API を利用できます。

  1. ClientHTTP リクエストを送信
  2. Controller認証・認可の適用後に入力を受け付ける
  3. Manager所有者や招待コードの状態を確認し、処理を実行
  4. PostgreSQLEF Core と Npgsql 経由で取得・保存

実装で工夫したこと

操作権限と所有者の確認

JWT の署名と有効期限を検証します。招待コードの発行はロールで制限し、レビューや建物を更新する際は現在のユーザーが登録者本人か、管理権限を持っているかを確認します。

いいねの重複を防ぐ

レビュー ID とユーザー ID を複合主キーにして、同じユーザーが同じレビューに複数の「いいね」を登録できないようにしました。切り替え時は「いいね」の行とレビューの件数を同じ保存処理で更新します。

関連データの削除ルール

外部キーごとに削除時の動作を設定しました。たとえばレビューの削除時は関連する「いいね」を連動して削除し、レビューが参照する建物の削除は制限します。

一覧取得とレスポンスの整形

一覧取得にフィルターとページネーションを用意しました。参照用のクエリでは変更追跡を省略します。更新処理では AutoMapper を使い、入力 DTO の値をエンティティに反映し、更新後のデータを出力 DTO に変換します。

エラー応答の共通化

例外処理を起動設定にまとめ、権限エラー・対象データなし・状態の競合を、それぞれ HTTP 403・404・409 と JSON のメッセージに変換しています。

今後の改善点

会員登録はユーザーの作成と招待コードの使用済み更新を別々に保存しています。片方だけが保存される状態を防ぐため、両方を同一トランザクションで処理する余地があります。また、一部の管理 API はロール指定に master を使用しているため、実際に発行する manager とそろえる必要があります。
